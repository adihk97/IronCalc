# Incremental recalculation: smallest safe first step

This describes the checked-out code, not the 0.9.1 benchmark implementation. The proposed behavior is a design, not existing functionality. No Rust toolchain or network is available here; no build, tests, or benchmark was run.

## Current flow

- `Model::update_cell_with_text/bool/number/formula` write through cell setters (`base/src/model.rs:2365`, `:2413`, `:2455`, `:2500`). `Model::set_user_input` prepares the cell (including spill handling), parses input and writes or clears it (`model.rs:2530`, `:2637`). These raw APIs do not themselves call `evaluate`; their callers must do so. `UserModel::set_user_input` records diffs, calls the raw setter, then `evaluate_if_not_paused` (`base/src/user_model/common.rs:436`, `:470`, `:2315`). Pausing defers evaluation; `resume_evaluation` only clears the pause flag (`common.rs:381`); explicit `evaluate` calls the model (`:393`).
- There is no persistent operation marking all formulas dirty. `Model::evaluate` surveys formula-bearing sheets and gathers every formula (`base/src/evaluation.rs:519`, `:607`); each `run_pass` clears the per-pass cell-state map and evaluates every anchor and formula (`:708`). Thus every formula is eligible again, regardless of the edit. Recursive reads evaluate a formula first when needed; an already evaluated formula returns its stored value (`:750`, `:850`). Restarts may rerun a pass; conditional formatting is evaluated afterward (`:519`, `:552`).
- Cached results live in `CellFormula`/`ArrayFormula` and `SpillCell`; `FormulaValue::Unevaluated` also exists (`base/src/types.rs:290`, `:352`). The separate `Evaluation.cells` tracks `Evaluating` and `Evaluated` for the current pass, and detects a cycle when an evaluating cell is read (`evaluation.rs:125`, `:857`). `run_top` writes results and updates that state (`:939`). Incremental evaluation must preserve valid cached values, distinguish dirty from clean and in-progress, and handle errors, cycle recovery, spill ownership and side effects as well as values.

## References and invalidation hazards

- `evaluate_node_in_context` resolves relative/absolute references using the formula position and sheet index; a range becomes a normalized rectangle (`model.rs:797`, `:826`). Defined names can resolve to cells, ranges, formulas or lambdas (`:925`). `evaluate_range` walks rows (`:1692`); `SUM` clips to used area then loops through cells (`base/src/functions/math_and_trigonometry/mathematical.rs:260`, `:307`). Whole-column/row clipping must still track the *original* rectangle, including currently empty positions (`evaluation.rs:1050`, `:1085`). Sheet-qualified references are indexed by sheet as well as coordinates.
- `INDIRECT` parses a reference from evaluated text and `OFFSET` calculates a reference from arguments (`base/src/functions/lookup_and_reference/mod.rs:918`, `:966`): their targets can change at runtime. Conditional branches, defined-name formulas and lambdas also mean executed reads need not equal syntactic references. `NOW` reads time and `RAND` generates a random value (`base/src/functions/date_and_time.rs:1340`; `base/src/functions/math_and_trigonometry/random.rs:20`); the present full pass reevaluates them. An incremental implementation needs a complete volatile classification, including names and nested calls, or must fall back.
- Array anchors write spill cells; dynamic spills can change shape, collide, require pass restarts, and make reads of old spill cells special (`evaluation.rs:519`, `:791`; `model.rs:1097`). Existing `seen`/`seen_ranges` serve spill contradiction detection, not a persistent dependency index: they are pass-local, record reads only with dynamic anchors, and ranges there can be attributed to the root (`evaluation.rs:708`, `:1044`). Do not reuse them as complete formula-to-input edges.
- Structural changes include row/column insert and delete (`base/src/actions.rs:704`, `:817`, `:1069`, `:1164`), sheet delete, rename and move (`user_model/common.rs:632`, `:656`, `:674`), clipboard moves and formula/name rewrites (`base/src/user_model/clipboard.rs:188`, `:584`; `base/src/cut_paste.rs:160`, `:248`), merge (`user_model/merged_cells.rs:59`), defined-name changes (`user_model/common.rs:2136`), undo/redo and external diffs (`common.rs:334`, `:349`, `:415`). These can move cells, alter references, or bypass a simple edit hook. Invalidate conservatively at the lower mutation boundary, including partial failure paths, not just UI wrappers. Audit all other mutation APIs, including direct public workbook access, before enabling incremental mode.
- `Model::from_workbook` parses formulas and names and initializes fresh evaluation state, but does not evaluate all formulas (`model.rs:1937`, `:1988`); `from_bytes` delegates to it (`:1913`). XLSX import constructs a model this way (`xlsx/src/import/mod.rs:190`); Python, Node and WASM bindings also construct/wrap models (`bindings/python/src/user_model.rs:37`; `bindings/nodejs/src/user_model.rs:46`; `bindings/wasm/src/lib.rs:146`). An imported cache is not an index: start invalid and build via a successful full evaluation before incremental edits, or use a proven complete separate build.

## Proposed minimal safe design

### Direct workbook mutation

Incremental recalculation is opt-in. `Model::workbook` remains public for
compatibility, but direct mutation bypasses the model edit hooks. Call
`Model::invalidate_dependency_index()` after such a mutation; the next
evaluation will use the full evaluator and rebuild the records.

1. Add non-serialized model-owned index state: invalid, or valid with forward reads per formula and reverse point/rectangle lookup per sheet. Key by sheet, row and column. Capture a formula's own reads while it runs, including empty cells; register each range as one inclusive rectangle in a point-stabbing index, not one edge per member. Instrument every range consumer and optimized bulk path, not just `evaluate_cell`: `evaluate_range_of_numbers` can copy numeric rows directly (`model.rs:1719`). Preserve a full range even if a function exits early or clips it. A formula can be conservatively associated with more inputs than actually read. Index collection must be complete for supported formulas and transactional across unwind/replay and abandoned spill passes; replace old edges only after a successful result. Record reads under the current formula stack frame, not merely the pass root.
2. Start narrowly: enable the fast path only for a proven subset of scalar formulas and ordinary value/formula edits with complete instrumentation. If coverage is uncertain, if the index is invalid, or if a workbook contains dynamic references, spills, unsupported functions or unclassified volatility, use the existing full evaluation and rebuild a complete index only when safe. Structural/name/sheet/clipboard/merge/history changes invalidate the index and force the next evaluation through the full path. The index must remain invalid until a successful supported rebuild. A formula replacement removes its old outgoing reads and dirties the cell and its dependents; replacing a formula with a constant removes those reads too. Multiple edits while paused accumulate changes.
3. On edit, query point readers and rectangles containing the changed coordinate, then traverse their dependents transitively with a deduplicated queue. Dirty even when the previous value was empty, an error, or a formula. Mark volatile formulas and their transitive dependents dirty on each recalculation; until classification is complete, use the full path. Explicit `evaluate()` must retain its current recalculation semantics. Do not rely on unchanged intermediate values for pruning in the initial version.

### Incremental work budget

The current rectangle lookup is a flat per-sheet scan. The incremental path
therefore refuses an edit before scanning a sheet with more than 1,000
rectangle edges, and also refuses once the dirty set exceeds `max(1,000, 10%`
of indexed formula records). Both cases run the ordinary full evaluator. These
are correctness-preserving performance guards until the rectangle index gains
a sublinear point-stabbing implementation.
4. Evaluate dirty formulas with the existing demand recursion: a dirty precedent evaluates before its reader; a clean formula returns its cached result. Keep the current in-progress cycle detection and replay depth limit, but scope pass state so clean caches are valid. Rebuild edges after successful evaluation; cycles need tests for both introduction and removal. Any unsupported spill/restart or uncertain state discards the partial incremental attempt and runs the existing full evaluator. Keep conditional-formatting evaluation and dynamic link behavior correct: the full pass clears and rebuilds links (`evaluation.rs:727`), so an incremental pass must preserve clean links and refresh dirty ones, or fall back.

For the stated A..Y/Z/AA workload, this finds Z of the edited row and AA1 without running every Z formula. **It does not make total edit time proportional only to the number of affected formulas:** AA1's existing `SUM` still scans A1:A{rows}. Meeting that stronger goal needs a separate incremental aggregate or range-summary design, including numeric ordering, errors, type changes and floating-point semantics. A rectangle index alone does not provide it. Index construction and any full-workbook survey must also be kept off the steady-state edit path.

## Stages and tests to write

Tests are proposals under `base/src/test`; none were run here. At each stage compare the incremental result with a fresh full-evaluation oracle, including errors and visible side effects.

1. Add instrumentation and an initially disabled index; test direct, empty, cross-sheet, named and relative references, whole columns and range boundaries, shared formulas at different positions, and numeric bulk reads. Confirm a rectangle takes bounded index entries. Test branch changes, early errors, replay and abandoned passes for stale edges.
2. Add invalidation and dirty recursion for the proven scalar subset; test chains, diamonds, unrelated formulas, formula replacement/deletion, cycles introduced and removed, paused batches and repeated edits. Instrument formula executions to assert only expected formulas run. Compare full versus incremental across sequences, not just one edit.
3. Add conservative fallback at every mutation and load boundary. Test insert/delete, cut/paste, rename/delete/move sheet, defined names, merge, undo/redo, external diffs, and import; exercise failure and subsequent edits. Test `INDIRECT`, `OFFSET`, volatile functions, arrays/spills and conditional formatting against full evaluation. Reuse existing suites under `base/src/test/dynamic_evaluation`, `array_formulas`, `test_circular_references.rs` and `test_actions.rs`.
4. With a Rust toolchain installed, run the relevant base and workspace tests, formatting and lint checks, then benchmark the supplied three sizes, separating initial index build, A edit, Z read and AA1 read; compare full and incremental results. Measure memory and rectangle-query cost, formula executions and SUM scan cost. Add representative sparse/whole-column, long-chain and spill workloads. The background timings have not been reproduced here.

## Questions for issue #849

- Should explicit `evaluate()` always recalculate volatile formulas as today, and what is the authoritative complete volatile-function list, including calls through names and lambdas?
- Can incremental support initially exclude any workbook containing dynamic arrays, `INDIRECT` or `OFFSET`, and should fallback be workbook-wide or per formula?
- What public mutation and direct workbook-access contracts can guarantee that index invalidation cannot be bypassed, including failed mutations and imported/externally applied diffs?
- Is a separate incremental SUM/range aggregate acceptable for the target workload, given current full-range scanning and floating-point/error semantics?
- Should conditional formatting and dynamic hyperlinks be included in the first correctness milestone, or force full evaluation when present?
